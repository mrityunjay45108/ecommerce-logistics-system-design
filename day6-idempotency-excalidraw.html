Idempotency in Production Systems

Same Request ≠ Duplicate Operation
Build for retries, not just success.
In distributed systems, network failures, retries and timeouts are normal. Idempotency ensures that even if the same request is made multiple times, the final result is the same — only one operation is performed.

💜 Where Do We Need Idempotency?
💳 Payment ➔ Idempotency-Key
📦 Order ➔ Unique Checkout Ref
🚚 Shipment ➔ externalOrderId
🌐 Webhook ➔ eventId (Inbox)
⚡ Kafka Consumer ➔ eventId (Deduplication)
Key Database Constraints
  • UNIQUE(provider, idempotencyKey)
  • UNIQUE(sellerId, externalOrderId)
  • UNIQUE(paymentProvider, transactionId)
  • UNIQUE(eventId, consumerGroup)
  • • Proper indexes for fast lookup
💡 The Big Lesson
Idempotency is not just a Redis key. For critical operations, use:
☑ Database constraints
☑ Transactional outbox
☑ Idempotent business logic
Exactly-once behavior is achieved through idempotent processing, not by assuming the network will deliver exactly once.
