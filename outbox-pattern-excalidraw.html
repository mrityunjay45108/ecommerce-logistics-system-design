Transactional Outbox Pattern

Ensure database changes and event publishing happen reliably and atomically.
The outbox pattern solves the dual-write problem by storing events in the same database transaction as the business data. Events are published asynchronously by a background worker.

Step-by-Step Flow
1 Start Transaction
Business logic starts (e.g. create order, update shipment).
2 Update Database
Update business data, create tracking logs, insert outbox event.
3 Commit
All changes (data + outbox) are committed atomically.
4 Publish Event
Outbox worker reads pending events and publishes to Kafka.
5 Update Status
Mark event as PUBLISHED. If failed, retry later.
6 Consumers Process
E-commerce, Logistics, Notifications, Analytics consume the event.
✅ Why It's Important?
  • Ensures database and event consistency
  • Prevents lost events
  • Handles Kafka downtime gracefully
  • Provides retry capability
  • Improves system reliability and auditability
  • Supports event-driven architecture
❗ What Happens If Kafka Is Down?
🗄️ Event saved in outbox (PENDING)
▼
🔄 Outbox worker retries
▼
⚡ When Kafka is available ➔ event is published
▼
✔ Status updated to PUBLISHED
ℹ️ Important Note
Transactional Outbox does NOT give exactly-once delivery.
For true reliability, combine it with:
At-Least-Once Delivery (Kafka)
