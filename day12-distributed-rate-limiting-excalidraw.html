DISTRIBUTED RATE LIMITING WITH REDIS

Same limit. All instances. No loopholes.
A distributed rate limiter uses Redis to share the same state across multiple API servers, ensuring consistent and fair traffic control.
💡 Why Redis?
  • ✔ Shared state across instances
  • ✔ Very low latency
  • ✔ Atomic operations
  • ✔ Key expiration (TTL)
  • ✔ Lua scripting for complex logic

🪣 Token Bucket Algorithm
  • 1 Bucket capacity = Burst limit
  • 2 Refill tokens at a fixed rate
  • 3 Each request consumes 1 token
  • 4 If token available ➔ Allow
  • 5 If empty ➔ Deny (429)
</> Atomicity with Redis Lua
Use Redis Lua / EVAL for atomic read ➔ decide ➔ update.
  • 1 Read (GET)
  • 2 Decide (check limit)
  • 3 Update (INCR + EXPIRE)
🛡️ Prevents race conditions:
(e.g., double-spending tokens, lost updates).

⚙️ Rate Limiting Algorithms
Algorithm Key Feature
Fixed Window ➔ Simple, easy
Sliding Window ➔ Smoother, accurate
Token Bucket ➔ Controlled bursts
Leaky Bucket ➔ Steady rate, no burst
🔗 Rate Limiting vs Others
Rate Limiting ➔ Ingress control
Throttling ➔ Reject excess
Retry ➔ Try again
Timeout ➔ Don't wait forever
Circuit Breaker ➔ Stop failing calls
Bulkhead ➔ Isolate resources
🚀 Key Takeaway:
“In a distributed system, rate limiting must be distributed too.”
